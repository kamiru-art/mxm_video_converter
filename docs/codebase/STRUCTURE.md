# Codebase Structure

## 1) Top-Level Map

| Path | Purpose | Evidence |
|------|---------|----------|
| `rust-core/` | The image processing core. Rust, compiled to WebAssembly. No browser code. | `rust-core/Cargo.toml` |
| `rust-core/src/` | 18 domain modules plus the WebAssembly boundary. | `rust-core/src/lib.rs` |
| `rust-core/assets/` | `DejaVuSans.ttf`, embedded with `include_bytes!`, and its license notice. | `rust-core/src/text.rs` |
| `rust-core/tests/` | The end-to-end integration test. | `rust-core/tests/pipeline.rs` |
| `web/` | The web application. No framework. | `web/package.json` |
| `web/src/` | The interface, the worker pool, the video extraction (`video.ts`, `avi.ts`, `frames.ts`, `opfs.ts`), the lossless export (`export.ts`, `pngmov.ts`, `player.ts`, `imageinfo.ts`), the compressed MP4 (`lossy.ts`), the service worker (`sw.ts`) and the import of data from the old address (`migrate.ts`). | `web/src/main.ts` |
| `web/*.mts` | Node scripts, run as TypeScript by Node's type stripping: the build helpers (`prepare-ffmpeg.mts`, `make-icons.mts`, `carry-assets.mts`) and the three browser suites (`e2e-run.mts` + `e2e-verify.mts`, `e2e-ui.mts`, `e2e-migration.mts`, sharing `e2e-browsers.mts`). | `web/package.json`, `web/tsconfig.node.json` |

| `.github/workflows/` | One workflow: test, then build, then deploy. | `.github/workflows/ci.yml` |

## 2) Entry Points

- Main runtime entry: `web/index.html`, which loads `web/src/main.ts`.
- `web/src/main.ts` mounts one phase module on demand and keeps the route in
  `location.hash`.
- Worker entry: `web/src/worker.ts`. The pool starts it with
  `new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })`
  (`web/src/pool.ts`).
- WebAssembly entry: `rust-core/src/api.rs`. It holds the 26 `#[wasm_bindgen]`
  items and is the only module the TypeScript side calls.
- Test entries: `web/e2e.html` with `web/src/e2e.ts`, driven by `web/e2e-run.mts`
  (checked from outside by `web/e2e-verify.mts`); the interface test
  `web/e2e-ui.mts` drives `web/index.html`. Both use `web/e2e-browsers.mts`.
- Deploy-time entry: `web/carry-assets.mts https://mxmstudio.work dist`, run by CI between the build and `wrangler deploy` (see `ARCHITECTURE.md` §4).
- Build-time entry: `web/prepare-ffmpeg.mts` copies the ffmpeg cores out of
  `node_modules` into content-addressed directories
  (`web/public/ffmpeg/st-<hash>/`, `mt-<hash>/`) with a `manifest.json` in
  `st/` and `mt/` that names them. `npm run dev` does not run it.

## 3) Module Boundaries

| Boundary | What belongs here | What must not be here |
|----------|-------------------|------------------------|
| `rust-core/src/` domain modules (`sheet`, `photo`, `scanproc`, `conform`, `cyanotype`, `aruco`, `qr`, `calib`, `geometry`, `img`, `imgproc`, `codecs`, `dedup`, `pdf`, `text`, `layoutfile`, `yuv`) | Pure image and geometry work. Plain Rust types. | `wasm_bindgen`, browser types, input and output. |
| `rust-core/src/api.rs` | The WebAssembly boundary: argument validation, JSON to typed values, `Result<_, JsValue>`. | Image algorithms. |
| `web/src/pool.ts` | Worker lifetime, dispatch, memory recycling. | Anything about the interface. |
| `web/src/worker.ts` | A command name to core function table. | Business rules. |
| `web/src/phase*.ts` | The DOM of one phase and its event handling. | Direct WebAssembly calls; everything goes through `run()`. |
| `web/src/project.ts` | The state shared between phases, in memory, and the on-demand decoding of frames that live in their video. | Persistence. |
| `web/src/opfs.ts` | The only writer of the browser's private file system: the PNG cache of frames decoded by `ffmpeg.wasm`, and the output files (the ZIP and the PDF) written chunk by chunk. | Anything else. |
| `web/src/export.ts` | The final video: plans the sequence, conforms what must be conformed in the pool, writes the MOV (`pngmov.ts`) or the PNG ZIP, decodes the original sound. | Any lossy codec (that is `lossy.ts`). |
| `web/src/lossy.ts` | The compressed MP4: presets and fixed bitrate, codec choice, frame decoding ahead of the encoder, sound. | Planning the sequence (reuses `export.ts`). |
| `web/src/zip.ts` | The streaming ZIP writer (`ZipSink`) and `makeZip` on top of it. | Deciding what goes in. |
| `web/src/store.ts` | The reader and writer of the main `localStorage` key, `mxm-studio-v1`, and of `mxm_ram_gb` (`loadRam`, `saveRam`). The one other key, `mxm-migrated-ids`, belongs to `migrate.ts`. Every access is inside `try`. | Anything else. |
| `web/src/migrate.ts` | Reading the `#mxm-migrate=` fragment the old address sends, merging it through `store.ts`, restoring the route. Runs before anything reads the route or the store. | Anything after startup. |

## 4) Naming and Organization Rules

- Rust files: `snake_case.rs`, one module for each domain area
  (`scanproc.rs`, `cyanotype.rs`). Declared in `rust-core/src/lib.rs`.
- TypeScript files: lowercase, no separator, with a number for the phases
  (`phase1.ts`, `pool.ts`, `webgpu.ts`).
- Each phase module exports one `mount<Name>` function that receives its root
  element: `mountPhase1(rootEl)` (`web/src/main.ts`).
- Organisation is by workflow phase, not by layer or by type. Phase 1 is the
  sheets, phase 2 the scans, phase 3 the calibration, phase 4 the video. The
  route names do not follow the numbers: `sheets`, `scans`, `calibration`,
  `video`, `help` (`web/src/main.ts`).
- Imports are relative, with an explicit `.ts` extension. There is no alias
  and no barrel file.
- The service worker is `web/src/sw.ts`, a second Vite entry that is emitted
  as `/sw.js` (`web/vite.config.ts`), the fixed name `main.ts` registers.
- The old Spanish routes still resolve, through the `LEGACY_ROUTES` table in
  `web/src/main.ts`, so that saved links keep working.
